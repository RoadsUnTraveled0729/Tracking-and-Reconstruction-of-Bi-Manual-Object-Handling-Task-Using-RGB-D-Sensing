# v1: the thesis pipeline (frozen reference implementation)

## Purpose

v1 answers the thesis question: can one RGB-D camera track a bi-manual
object-handling task accurately enough to reconstruct it, live, in a
game engine, while being honest about occlusion? It is the version the
thesis reports; every number in the manuscript traces to a v1
validator or profiler output pinned in the repository. There is no
earlier version; v2 and v3 both build on it by importing or copying,
never by editing.

## Status

FROZEN at git tag v1-thesis. Results are trustworthy: every stage has
a validation script whose output is committed, and the v2 track later
reproduced the v1 numbers bit-for-bit through an independent transport
(v2/dataset/m2_pipeline_parity.txt).

v1 lives under v1/ (mediapipe/, kinematics/, aruco/, realtime/,
integration/, unity_bridge/), moved there from the repo root on
2026-08-25 with history preserved; the v1 Unity scenes remain in the
shared Unity/ project. This file is its version README.

## Design decisions

Recorded in .agent/DECISIONS.md (thesis-track log); the load-bearing
five:

- Swing-twist joint parameterization with the twist innermost
  (KINEMATIC_MODEL.md section 6): 3 landmarks per arm give exactly 4
  observable rotational DOF; the parameterization makes the
  unobservable part explicit instead of hiding it.
- Left arm defined by sagittal mirroring of the right-arm solver
  (KINEMATIC_MODEL.md section 9): one solver, provably symmetric
  angle meanings.
- Chain-fallback occlusion handling (kinematics/occlusion.py): a
  blocked landmark freezes only the joints that need it, in angle
  space (bone-length consistent), never in point space.
- A/B independence: person and object pipelines share nothing but the
  sensor stream and the clock, so one failing cannot corrupt the
  other (INTEGRATION.md).
- Unity applies numbers, never creates them: every rendered quantity
  arrives through a versioned shared-memory packet with liveness
  flags; red rendering means "not measured", visibly.

## Results

Conditions: the pinned recording (Video/recording_20260224_083945.bag,
899 frames, 640x480 at 30 fps, one subject, cube with ArUco marker),
solved causally at recorded pacing on the development machine.

- Real-time causal solve vs the offline reference: worst joint-group
  median 0.64 deg / p95 3.24 deg, 3 frames lag; pelvis median 2.4 mm;
  object median 6.2 mm (reproduced in v2/dataset/m3_validate_output
  .txt).
- 97.3 percent of post-warm-up frames fully live; the rest are held
  honestly and shown red.
- Stage budgets: person pipeline p99 about 28 ms, object p99 about
  14.5 ms per frame, within the 33.3 ms frame interval.
- Synthetic-occlusion suite: 33 checks over six masked scenarios
  (wrist short/long, elbow, hip, root reference, full pose loss), all
  PASS (kinematics/validate_occlusion.py).
- What failed along the way is recorded in .agent/DECISIONS.md; the
  notable standing limitation is below.

## Limitations

- Long occlusions freeze the affected joints (by design); there is no
  recovery estimate. This is the gap v3 investigates.
- MediaPipe visibility gating at 0.5 is detector-specific and does
  not transfer to other detectors (measured in the v3 track).
- Single person, single rigid object, fixed camera, marker on the
  object.

## How to reproduce

    # validation suites on the pinned recording and synthetic data
    # (run from the repo root)
    python v1/kinematics/validate_real_recording.py   # end-to-end bounds
    python v1/kinematics/validate_occlusion.py        # 33-check suite
    python v1/kinematics/validate_shoulder.py         # solver identities

    # the recording-paced real-time stage
    python v1/realtime/person/realtime_person.py --help

The exact per-stage commands and their pinned outputs are indexed in
.agent/STATE.md (thesis track).
